Folderss · 두 파일 비교 엔진 검토

diff 엔진 벤치마크

⚠ Linux 측정 · Windows 재측정 전

앱의 두 파일 비교는 지금 매번 git diff --no-index 프로세스를 띄웁니다. 같은 일을 프로세스 안에서 하는 후보 5가지를 20가지 경우로 측정해 비교했습니다. 앱 코드는 바꾸지 않았습니다.

결론

  • 보통 수정은 프로세스 안 방식이 빠름1줄 수정·블록 추가·곳곳 1% 수정 등 12건, 관리 코드 4방식의 중앙값입니다. git 시간의 대부분은 프로세스를 띄우는 고정 비용입니다.
  • 최악 경우는 git이 압도적전부 다름·50% 수정·줄 끝 변경 4건, 관리 코드 4방식의 중앙값입니다(최대 약 40×). git(xdiff)은 한쪽에만 있는 줄을 미리 걸러 내는 것으로 보입니다(추정).
  • 결과 품질은 사실상 같음19 / 20변경 줄 수가 모든 방식에서 같았습니다. 순서를 뒤섞은 경우만 다릅니다.
  • LibGit2Sharp는 오히려 느림엔진은 git과 같지만, 비교마다 두 파일을 압축해 저장소에 써야 합니다.

방식별 요약

20건 시간의 git CLI 대비 기하평균입니다. 1.0보다 크면 git보다 빠릅니다. 막대에 마우스를 올리면 합계·최고 기록 횟수를 볼 수 있습니다.

방식종류20건 합계 (ms)git 대비가장 빠름지원 안 함

경우별 시간

칸의 숫자는 중앙값(ms)이고, 아래 줄은 git CLI 대비 배수입니다. 파랑은 git보다 빠름, 빨강은 git보다 느림이며 진할수록 차이가 큽니다. 칸에 마우스를 올리거나 Tab으로 이동하면 변경 줄 수·메모리를 볼 수 있습니다.

결과 품질 (변경 줄 수 = 삭제 + 추가)

관리 코드 4가지는 결과로 옛 파일을 새 파일로 정확히 재구성되는지 매 경우 확인했습니다. 19건은 여섯 방식이 모두 같은 줄 수를 냈고, 다른 1건은 아래와 같습니다.

Myers 계열이 최소(3,826줄)입니다. git은 비용 상한 휴리스틱 때문에 26줄 더 많고, Histogram은 드문 줄을 기준점으로 삼는 방식이라 150줄 더 많습니다.

메모리 (관리 힙, 1회)

git CLI는 별도 프로세스이고 LibGit2Sharp는 네이티브 메모리를 써서 거의 잡히지 않습니다. 관리 코드 방식은 파일 크기의 약 10배를 할당합니다.

방식별 판단

git CLI (현재)최악 경우에 강하고 결과도 검증돼 있습니다. 약점은 git 설치가 필수라는 점과, 매번 프로세스를 띄우는 고정 비용입니다(Windows에서 더 큼).
직접 Histogram기하평균 1위(1.4배)입니다. 그대로는 최악 경우가 수백 ms라 교체하기 어렵습니다. xdiff처럼 한쪽에만 있는 줄을 미리 거르고 비용 상한을 두는 처리, 바이트 동일 선검사, 공백 무시, unified 출력이 함께 필요합니다.
DiffPlex안정적인 라이브러리입니다(Apache-2.0). 3-way 병합(ThreeWayDiffer)이 들어 있어 병합 기능을 다시 검토할 때 의미가 있습니다. 속도는 직접 Myers와 비슷하고, 최악 경우 문제도 같습니다.
직접 Myers2만 건 무작위 검사에서 늘 최소 결과를 냈습니다. 속도와 한계는 DiffPlex와 같아 따로 둘 이유는 적습니다.
diff-match-patch비추천입니다. NuGet 판마다 대상이 최신 .NET 하나뿐이라 .NET 8 앱은 3.0에 묶입니다. 줄 단위 API가 없고, 고유 줄이 약 6만 3천 개를 넘으면 쓸 수 없습니다(10만 줄 2건 실패).
LibGit2Sharp비추천입니다. 두 버퍼를 바로 비교하는 API가 없어 비교마다 blob을 저장소에 써야 하고, 그 비용이 가장 큽니다.

이 결과를 읽을 때 주의할 점

  • Linux 측정입니다. 여기서 git 프로세스를 띄우는 비용은 약 3.5ms입니다. Windows는 보통 이보다 비싸고 백신 실시간 검사가 끼면 더 늘어납니다. 그래서 Windows에서는 보통 수정의 차이가 더 벌어지고, 최악 경우의 격차는 줄어들 가능성이 큽니다.
  • 1ms 아래 값은 측정 잡음이 큽니다. 순위보다 자릿수 차이로 읽어야 합니다.
  • 같은 10만 줄 파일에서 관리 코드 방식이 80~124ms 걸린 것은 diff 알고리즘이 아니라 파일 전체를 읽고 줄로 나누는 비용 때문입니다. 바이트가 같은지 먼저 확인하면 피할 수 있습니다.
  • 줄 끝(LF↔CRLF) 경우는 모든 방식이 1만 줄 전부를 다르다고 봅니다. 앱의 "공백 무시"를 대체하려면 프로세스 안 방식도 같은 정규화를 직접 넣어야 합니다.

측정 방법과 재현

  • 경우마다 두 파일을 디스크에 써 두고, 파일 읽기부터 결과까지를 잽니다. 앱의 두 파일 비교와 같은 조건입니다.
  • 방식마다 첫 실행(JIT·결과 검증)을 뺀 뒤 최대 5회(3초를 넘으면 중단)의 중앙값을 씁니다.
  • git CLI는 앱과 같은 인수(--no-index --no-color --no-ext-diff -M, 문맥 3줄)를 씁니다.
  • 테스트 20가지는 고정 씨앗으로 만들어 매번 같습니다. 직접 구현은 무작위 2만 건으로 재구성 정확성과 Myers 최소성을 따로 검사했습니다.
