## 원인 분석 또는 설계

### 1. 자료 평가 — 쓸 수 있는 것과 없는 것

**출처 위험**: 자료는 상용 프로그램 실행 파일을 Ghidra로 디컴파일한 결과다. 상용 EULA는 보통 리버스 엔지니어링을 금지하므로,
자료의 함수 주소·필드 오프셋·상태 번호를 코드나 주석에 옮기지 않는다. 묶음(zip)도 저장소에 넣지 않는다.
설계 근거는 공식 도움말(`directory-compare.md`의 조사 자료 링크)과 일반 알고리즘으로 둔다.
자료에 들어 있는 라이선스 키 처리 분석은 이 작업과 무관하므로 참고하지 않는다.

**증거 수준**: 자료 스스로 핵심이 미확인이라고 적는다. 이름 비교 규칙, 시각 허용 오차, 빠른 서명(`+0xd8`) 생성 방식,
상태 1/2/3의 의미, 부모 집계표, 동기화 계획 알고리즘이 모두 그렇다. 확인된 것은 구조(최대 4쪽, 작업 캐시, 단계 분리)뿐이다.
게다가 그 구조의 대부분은 현재 코드에 이미 있다. 정리하면 자료는 "무엇을 구현할지"를 정해 주지 않고, 결정은 사용자 요구로 내려야 한다.

| 자료의 단계 | 현재 코드 | 차이 |
|---|---|---|
| A. 쪽별 열거 → 같은 항목 짝짓기 | `DirectoryCompareService.Walker.List` + 이름 합집합(대소문자 무시) | 없음. 폴더마다 사전으로 짝지으므로 정렬 병합(merge-join)은 필요 없다 |
| B. 필터·적격성 | `IgnoreRuleSet`, `IncludeHidden`, 한쪽만 ignore 표시 | 없음 |
| C. 노드별 비동기 작업 캐시·점진 표시 | 없음. 전체를 스캔한 뒤 한 번에 표시하고, 취소하면 부분 결과를 보인다 | 큰 폴더에서 첫 화면이 늦다. 병합과 무관하므로 **보류** |
| D. 싼 비교 먼저, 필요하면 내용 비교 | 크기를 본 뒤 SHA-256(옵션) **또는** 수정 시각으로 판정 | ① 크기가 같고 시각만 다른 파일(checkout·복사로 시각만 바뀐 경우)을 내용으로 다시 확인하는 모드가 없다. 그래서 모두 "다름"이 된다. 병합에서는 이 오탐이 곧 불필요한 덮어쓰기로 이어진다. ② 해시는 두 파일을 끝까지 읽는다. 바이트를 차례로 비교하면 첫 차이에서 멈출 수 있다 |
| E. 부모 상태 집계 | `Walker.Merge` (다름 > 비교 불가 > 같음) | 없음 |
| 4쪽 모델 | `CompareEntry`가 Left/Right 고정 | 3-way 병합(기준 폴더)을 할 때만 필요 |

### 2. 병합의 의미 — 선택지 (미결 핵심)

| 안 | 내용 | 규모 | 주요 위험 |
|---|---|---|---|
| **M-A 폴더 동기화(2-way)** | 비교 결과에서 작업 계획(복사·교체·삭제)을 만들고, 미리 보기로 확인한 뒤 실행한다. 방식: 왼쪽→오른쪽 갱신(새 파일·더 최신만), 미러(대상에만 있는 것은 삭제), 양방향 갱신 | 중 | 이전 결정(`directory-compare.md` 범위 밖: 동기화 프리셋)을 뒤집는다. 미러·양방향은 데이터를 잃을 수 있다(아래 4절) |
| **M-B 텍스트 파일 2-way 병합** | 두 파일의 변경 덩어리(hunk)마다 왼쪽/오른쪽 중 하나를 골라 결과를 저장한다 | 중~대 | 현재 diff 뷰(`GitDiffView`)는 unified 형식의 읽기 전용이다. 좌우 나란히 편집 화면은 새 UI다. 저장할 때 인코딩·BOM·줄 끝을 보존해야 한다 |
| M-C 텍스트 3-way 병합 | 기준(base)·왼쪽·오른쪽으로 결과를 만들고 충돌을 해결한다. `git merge-file -p --diff3`를 쓴다 | 중 | 폴더 비교에는 기준 파일이 없다. Git 충돌 해결에서만 의미가 있으므로 들어갈 곳은 Git 창이다 |
| M-D 3-way 폴더 병합 | 기준·왼쪽·오른쪽 폴더로 출력 폴더를 만든다 | 대 | `CompareEntry`·`CompareOverlay`·비교 창 전부를 N쪽으로 바꿔야 한다. 현재 2패널 설계와 맞지 않는다. 쓰는 경우가 드물다 |

**권장 순서**: P0(내용 재확인) → M-A → M-B. M-C와 M-D는 실제로 필요해질 때 따로 연다.

### 3. 단계별 계획 (완료 조건 = 테스트)

**P0. 판정 보강** (`DirectoryCompareService`, 옵션 1개)
- 옵션 `VerifyContentWhenTimeDiffers`(기본 켬은 미결)를 추가한다. 크기가 같고 시각만 다르면 바이트 비교로 다시 판정하며, 같으면 "같음(시각만 다름)" 사유를 단다.
- 내용 비교는 SHA-256 대신 두 스트림을 블록 단위로 비교해 첫 차이에서 멈춘다. `UseContentHash`의 의미("크기가 같으면 늘 내용 비교")는 그대로 둔다.
- 테스트: 내용이 같고 시각이 다른 쌍 → 옵션을 켜면 같음, 끄면 다름. 마지막 바이트만 다른 같은 크기 쌍 → 다름. 읽기 실패 → 비교 불가.

**P1. 동기화 계획기 `SyncPlanner`** (신규, 순수 로직, M-A)
- 입력은 `CompareResult`와 방식(갱신/미러/양방향), 출력은 `List<SyncAction>`(복사·교체·삭제·건너뜀+사유)이다.
- 규칙:
  - 유형 다름·비교 불가는 늘 건너뛰고 "충돌"로 표시한다.
  - 양쪽에 있는 폴더는 자식 단위로 계획한다.
  - 한쪽에만 있는 폴더는 통째로 복사한다.
  - 시각 방향은 기존 `CompareOverlay.GetDirection`(허용 오차)을 쓴다.
  - 양방향에서 양쪽 다 바뀌었을 수 있는 경우(기준이 없어 알 수 없음)는 "충돌"로 둔다.
- 테스트: 방식 × 상태(같음·다름-왼쪽최신·다름-오른쪽최신·왼쪽만·오른쪽만·유형 다름·비교 불가) 진리표를 모두 확인한다.

**P2. 동기화 미리 보기 대화상자** (`GitDialogBase` 상속)
- 방식 선택이 기능의 본질이므로 버튼이 곧바로 대화상자를 연다(CLAUDE.md 예외 규칙). 기본값은 가장 안전한 "왼쪽→오른쪽 갱신, 삭제 없음"이다.
- 삭제가 들어가는 방식(미러)은 경고와 확인 체크를 거친다. 계획 목록에서 항목별로 뺄 수 있다. 개수와 총 크기를 보인다.

**P3. 실행** (`FileOperationJournal` 확장)
- 계획 전체를 작업 이력 1건으로 실행해, 한 번 되돌리기로 전부 되돌린다(LIFO, 기존 규칙).
- 실행 직전에 항목마다 크기·시각을 다시 확인한다. 비교 뒤 바뀐 파일은 건너뛰고 로그에 남긴다.
- 교체·삭제는 휴지통으로 보낸다. 고정 드라이브가 아니면(휴지통 없음) 대화상자에서 미리 막거나 영구 삭제를 따로 확인받는다.
- 테스트: 계획 실행 → 결과 폴더 상태, 되돌리기 → 원상태, 실행 전에 바뀐 파일은 건너뜀.

**P4. 텍스트 2-way 병합 창** (M-B, P3 이후 별도 항목으로 분리 권장)
- 처음부터 diff 알고리즘을 만들지 않는다. `git diff --no-index -U0` 결과의 hunk를 단위로 쓰며, 결과는 "오른쪽 파일 + 고른 hunk만 왼쪽 내용으로 바꾼 것"이다.
- 결과 조립은 순수 함수로 두고 테스트한다. 입력은 hunk 목록과 선택이다.
- 저장할 때 원본의 인코딩·BOM·줄 끝을 유지한다. 바이너리이거나 10MB를 넘으면 기존 규칙대로 거부한다.
- 편집하는 동안 원본이 바뀌면 저장 전에 확인한다.

### 4. 위험·허점

- **삭제 계열(미러) = 데이터 손실 경로**: 네트워크·이동식 드라이브에는 휴지통이 없다. 그곳에서 미러를 실행하면 되돌릴 수 없는 영구 삭제가 된다.
- **시각 기반 "최신" 판단의 신뢰성**: 시계 차이, checkout·압축 해제로 시각이 새로 찍히는 경우, FAT 2초 해상도, DST 때문에 잘못될 수 있다. P0 없이 M-A를 하면 오래된 파일로 새 파일을 덮을 수 있다. 그래서 P0을 먼저 한다.
- **양방향 동기화는 기준 없이 판정할 수 없다**: 지난 동기화 상태(스냅샷)를 저장하지 않으면 "양쪽 다 수정"과 "한쪽만 수정"을 구분하지 못한다. 그래서 1차는 충돌로 두고, 스냅샷 저장은 별도 결정한다.
- **비교와 실행 사이의 변경(TOCTOU)**: 3단계의 실행 전 재검사로 막는다. 그래도 실행 도중의 변경은 막지 못한다.
- **기준이 겹칠 때**(한쪽 루트가 다른 쪽 안에 있을 때): 기존의 "원본을 품은 폴더는 교체하지 않음" 보호를 계획기에서도 지킨다.
- **대소문자만 다른 이름**: 짝짓기가 대소문자를 무시하므로, 복사할 때 대상 이름의 대소문자를 그대로 둘지 맞출지 정해야 한다(1차: 그대로 둠).
- **검증 환경**: 이 작업 환경은 Linux다. 순수 로직 테스트는 여기서 돌지만, WPF 화면·휴지통·실제 Windows 동작은 Windows에서 확인해야 한다.

### 미결 사항

1. merge의 뜻: M-A(폴더 동기화) / M-B(파일 병합) / 둘 다 / M-C·M-D.
2. M-A로 간다면 이전 결정인 "동기화 프리셋은 범위 밖"을 뒤집는 것이 맞는가. 미러(삭제 포함)까지 넣을 것인가.
3. P0 `VerifyContentWhenTimeDiffers`를 기본으로 켤 것인가. 켜면 정확하지만, 시각이 다른 같은 크기 파일을 모두 읽으므로 느리다.
4. 진입점: 기존 폴더 비교 창 툴바의 `동기화…` 버튼으로 둘 것인가(권장), 별도 창으로 둘 것인가.
